# 从一条 YouTube 链接到可复用的知识

[English](use-cases.md) · [返回中文 README](../README.zh-CN.md) · [架构说明](architecture.md) · [Provider 限制](providers.md)

> 本文中的视频标题、内容和笔记均为人工构造的教学示例，不对应真实频道、作者或视频。请在实际使用时粘贴你有权访问的视频链接。

## 为什么使用观澜

普通收藏解决的是“先把链接留下来”。但看完一小时的视频，一个月后想起其中某个观点时，你可能仍要重新打开视频、拖动进度条，再次寻找当时觉得重要的部分。

观澜试图把这段经历变成一条可审阅的知识工作流：保留原始来源，把可读原文与 AI 派生内容分开，让你决定哪些候选值得正式保存，并在以后有充分依据时把相关知识连接起来。学习笔记便于快速回顾，但不会取代来源；需要核查原话和语境时，仍应回到原始材料。

## 一条完整的 YouTube 工作流

假设我看到一段教学用示例视频：**《如何判断一个观点是否有可靠证据？》**。我的目标不是让 AI 自动替我下结论，而是保存来源、形成一份几分钟能读完的候选笔记，再由我决定是否入库。

### 1. 把视频交给观澜

我复制视频链接，在已经配置好观澜编排规则和相应采集工具的 Codex 环境中发送：

```text
采集
<YouTube 视频链接>
```

这是用户层面的自然语言操作示例，**不是公开仓库在任意 Codex 环境中自动注册的 CLI 命令**。它需要使用者自行配置 Codex 编排、Vault 路径和可用的采集 Provider。

这一步只应获取可验证的来源事实，而不是直接生成正式学习笔记。符合条件的结果会形成 Source Material 待审投影并进入 `00 收件箱`；它可以记录视频标题、原始链接、可用字幕或转录、证据引用、质量与缺失项，以及稳定的来源身份。

YouTube 支持取决于实际环境：可能需要外部下载工具、网络和来源权限，也可能需要可用字幕或单独配置的转录能力。字幕缺失、Provider 未配置、访问受限或证据不足时，流程应明确停止或要求补充条件，不能用 AI 猜测冒充视频原文。详细边界见 [Provider 支持范围](providers.md)。

### 2. 整理当前来源

采集结果具备可读内容、证据和质量校验后，我指定这条收件箱素材并发送：

```text
整理
00 收件箱中的《如何判断一个观点是否有可靠证据？》
```

如果收件箱里有多个待处理条目，应明确指定具体条目或 Source，不能让系统猜测。“整理”会生成一个状态为 `awaiting_user_confirmation` 的 Candidate Bundle，而不会直接写入正式目录。Bundle 可以同时包含：

- 忠实于来源的 Source Candidate；
- 与 Source 身份独立的 Learning Note Candidate；
- 其他类型是否适用、需要补证或被阻断的诚实判断。

整理不是把字幕机械压成一段摘要。它先保护可读来源，再为派生知识生成可审阅候选。下面是人工构造的候选片段，**不是实际视频转录或对真实作者的总结**：

```markdown
# 如何判断一个观点是否有可靠证据？

## 核心问题

怎样区分一个听起来有说服力的观点，与一个真正有证据支撑的观点？

## 来源主张

- 观点本身不等于证据。
- 判断论证时，需要检查证据来自哪里。
- 不同证据的可靠程度和适用范围可能不同。

## 可复用的理解框架｜AI结构化

以下框架由观澜根据来源进行结构化抽象，属于 AI_candidate，
并非来源逐条明确提出：先识别主张，再核查证据来源、适用条件与不确定性。

## 来源

指向本次采集的 Source Asset 与稳定证据引用。
```

这样的结果比单独保存链接更适合快速回顾；但当你要确认作者原话、限定条件或上下文时，仍应沿来源引用回查。只有证据本身提供时间信息时，系统才可能保留相应时间索引；不能假设每条笔记都能精确跳转到视频某一秒。

### 3. 审阅候选，再决定是否入库

Candidate 不是系统已经认定正确的最终知识。此时我需要检查：

- Source Candidate 是否忠实、完整，是否混入 AI 观点；
- Learning Candidate 是否误解或遗漏来源；
- AI 标注的概括与结构化是否合理；
- 哪些候选确实值得长期保存。

确认时，界面或编排层应展示当前 Candidate Bundle 及具体 Candidate。用户可以批准全部已展示且 `publishable` 的候选，也可以明确排除某项。例如：

```text
确认当前 Candidate Bundle 中展示的 Source Candidate 和 Learning Note Candidate。
入库
```

这同样是配置好的 Codex 环境中的用户操作，不是独立 CLI。正式 Publisher 会重新校验 Candidate 身份、Source revision、内容 hash、质量 Gate 和批准绑定；用户确认了哪一版，就只能发布被该批准精确绑定的那一版。`needs_corroboration`、`needs_validation`、`blocked` 或 `not_applicable` 的候选不会因为一句“入库”而绕过门禁。

### 4. 知识库最终得到什么

本例正式发布后，主要涉及三个位置：

- `00 收件箱`：待处理工作队列，不是正式知识资产类别；
- `10 原始资料`：保存经过确认、可追溯的 Source Asset；
- `20 学习笔记`：保存经过确认、适合快速阅读和再次使用的 Learning Note。

Source 与 Learning 是两个独立资产。学习笔记不会覆盖原始资料，也不能把 AI 的结构化内容倒写成作者原话。正式笔记保留稳定来源引用，使“快速阅读”和“回到证据”可以同时成立。完整目录职责见[架构说明](architecture.md)。

### 5. 按需整理关系图谱

假设知识库里已经有另一份人工构造的正式笔记：**《如何识别研究资料中的常见偏差？》**。它与本次笔记可能有关，但标题或关键词相似并不足以建立正式关系。

在已配置的 Codex 环境中，我可以主动发送：

```text
整理关系图谱
```

该操作对应 Relation Curation：只扫描符合范围的正式资产，根据稳定身份和语义证据发现候选。满足 Strong、高置信和证据门禁的关系可以由治理规则执行；Medium 候选进入观察池，不写入正式 Markdown；Weak 结果被过滤。Relation Registry 保存关系事实，Obsidian 内链只是展示投影。系统不会为了让图谱更密而自动连接所有相似文章。

如果两份示例笔记确实满足当前关系标准，读者可能看到类似的浏览路径：

```text
学习笔记 A：如何判断一个观点是否有可靠证据？
                    ↕
学习笔记 B：如何识别研究资料中的常见偏差？
```

这只是帮助理解的概念示意，不表示公开仓库或任何真实 Vault 已存在这条关系。

## 这些知识以后怎样发挥作用

几周后，我又读到一篇讨论证据判断的文章。我可以再次采集、整理、审阅和入库，并在需要时整理关系图谱。新内容不再只是另一个孤立收藏；它可以与已有正式知识形成经过证据门禁的联系，同时每份资产仍能回到自己的来源。

## 开始之前

真实 YouTube 场景需要正确配置 Codex 编排、Vault、外部采集工具、来源权限，以及可用字幕或转录能力；真实 AI 整理也依赖使用者配置的模型环境。公开仓库已经验证核心协议、空白 Vault 初始化、Source/Candidate/Publish/Relation 的合成流程，但尚未在空白环境复现包含全部可选 Provider 的真实生产安装。

请先阅读[项目 README](../README.zh-CN.md)、[Provider 限制](providers.md)和[架构说明](architecture.md)，再决定接入哪些真实来源。
